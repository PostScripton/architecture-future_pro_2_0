## Расширенный технический радар

<img src="/images/tasks/Task5Advanced/tech-radar.svg" alt="Расширенный технический радар Будущее 2.0: технологии и архитектурные паттерны по квадрантам и кольцам статуса Adopt, Trial, Assess, Hold"/>

Радар разбит на 4 квадранта и 4 кольца статуса.

Квадранты:

- Архитектурные паттерны.
- Хранение, платформа, облако.
- Интеграция и обработка данных.
- BI, доступ, наблюдаемость.

Кольца статуса:

- Adopt - применяем по умолчанию, целевой стандарт.
- Trial - внедряем на пилотах и в отдельных доменах, готовы масштабировать.
- Assess - изучаем прототипами, решение не принято.
- Hold - новых внедрений не начинать, действующее выводить по критериям.

Ключевые решения:

- В Adopt вынесены паттерны, на которых строится целевая архитектура: Event-Driven Architecture, Data Mesh, Domain-Driven Design с bounded contexts, Anticorruption Layer для легаси, Self-service BI как принцип.
- В Adopt по технологиям: Kafka как событийная шина, CDC через Debezium из SQL Server, DLQ, Schema Registry и контракты данных, Lakehouse на Iceberg поверх объектного хранилища, Kubernetes, Terraform, семантический слой метрик, ABAC с RLS и маскированием PII, lineage и каталог, наблюдаемость, CI/CD для данных.
- В Trial - то, что раскатывается через пилоты: дата-продукты с контрактами, Flink, Trino, ClickHouse для потоковых витрин, каталог данных, портал self-service BI, SLA и SLO для дата-продуктов, FinOps.
- В Assess - опции без принятого решения: Kappa и streaming-first, Data Fabric, serverless-запросы, Flink SQL как основной инструмент витрин, Headless BI, embedded analytics для партнёров.
- В Hold - легаси и антипаттерны: SQL Server 2008 как DWH, Camel ESB как основная интеграция, монолитный DWH с бизнес-логикой, синхронные точечные интеграции на критическом пути, PowerBuilder, Power BI с кастомизациями поверх DWH, ручные Excel-сверки.

Полный перечень с обоснованием по каждой позиции - в [tech-radar.md](tech-radar.md).

## TCO-анализ

Подробно - в [tco-analysis.md](tco-analysis.md). Сравниваются текущая архитектура (DWH на SQL Server 2008, ESB на Camel, Power BI, PowerBuilder) и целевая облачная событийная платформа с Data Mesh и порталом самообслуживания. Значения иллюстративные, в тыс. у.е., и служат для сравнения структуры и динамики затрат.

Статьи затрат: инфраструктура, лицензии и подписки, сопровождение и эксплуатация, время аналитиков и подготовка данных. Для целевого варианта добавлены разовые затраты программы трансформации и параллельный легаси-контур на период миграции.

Результаты:

- Текущая архитектура: 6000 в год с ростом около 10 процентов в год, итого за 3 года 19860.
- Целевая архитектура: пик инвестиций в 1-2 годах (8100 и 7000), в 3-м году 4370, итого за 3 года 19470.
- За 3 года варианты выходят примерно в паритет по деньгам, при этом целевая уже к 3-му году дешевле в эксплуатации.
- Годовой прогон после 3-го года: текущая около 7260 и растёт дальше, целевая около 3470 и снижается; годовая экономия с 4-го года около 3800-4000.
- Окупаемость затрат программы (4900) - в течение 4-го года. Экономия за 5 лет около 10860.
- Качественно: time-to-market отчётов с часов до минут, near-real-time вместо batch, снятие риска необслуживаемого SQL Server 2008, независимое масштабирование доменов.

## Роадмап внедрения Data Mesh

<img src="/images/tasks/Task5Advanced/roadmap.svg" alt="Стратегический роадмап внедрения Data Mesh Будущее 2.0: потоки работ по этапам подготовки, пилота, масштабирования и вывода легаси с привязкой к целям бизнеса"/>

Роадмап построен как матрица: строки - потоки работ (фаза программы, домены в Mesh, дата-продукты и витрины, платформа и governance, роли и команда, цели бизнеса), столбцы - этапы по времени.

Этапы согласованы с тремя фазами трансформации из кейса:

- Этап 0. Подготовка (0-3 мес): согласование решения, единые принципы событий и DLQ, каталог схем, нарезка границ доменов, платформенное ядро, формирование команды.
- Этап 1. Пилот (0-6 мес): 1-2 домена на событиях, MDM как Published Language, 3-5 дата-продуктов, первая версия портала self-service BI, семантический слой.
- Этап 2. Масштабирование (6-18 мес): критические домены, потоковые витрины near-real-time, антикоррупционные слои к Camel и DWH, партнёрская интеграция, конструктор отчётов для бизнес-пользователей.
- Этап 3. Поддержка и вывод легаси (18-36 мес): отказ от синхронных точечных интеграций, доменная аналитика на потоках, новые домены и регионы, вывод DWH и Camel по критериям.

Ключевые роли и зона ответственности:

- Data Product Owner - дата-продукт домена как продукт: ценность, бэклог, SLA и SLO, контракты данных, политики доступа.
- Data Engineer - пайплайны, потоковая и пакетная обработка, витрины, проверки качества, обработка DLQ на self-service платформе.
- BI-аналитик - перенос отчётов в портал, описание метрик в семантическом слое, витрины и дашборды поверх дата-продуктов, поддержка бизнес-пользователей.
- Поддерживающие: платформенная команда (платформа как продукт), Data Steward и governance-совет (федеративные стандарты и контроль), Domain SME (знание предметной области).

Привязка к целям бизнеса:

- Промежуточное состояние через пару месяцев (решение согласовано, границы доменов определены, проекты витрины запланированы) - этапы 0 и 1.
- Финальное состояние через год (портал самообслуживания реализован, бизнес-пользователи работают в новой архитектуре, легаси временно в отдельных доменах) - этап 2.
- Долгосрочная цель на 3 года (слабосвязанная событийная платформа, масштабирование по продуктам, географии и данным, near-real-time, Camel и DWH только как мосты) - этап 3.
