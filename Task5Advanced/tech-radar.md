# Расширенный технический радар "Будущее 2.0"

Целевой технологический стек платформы данных на горизонт 3 года. В радар включены и технологии, и архитектурные паттерны. Радар разбит на 4 квадранта и 4 кольца статуса.

## Кольца статуса

- Adopt - применяем по умолчанию, это целевой стандарт для новых решений.
- Trial - внедряем на пилотах и в отдельных доменах, есть готовность масштабировать при подтверждении.
- Assess - изучаем прототипами и PoC, решение о внедрении не принято.
- Hold - не начинать новых внедрений, действующее выводить из эксплуатации по критериям.

## Квадрант 1. Архитектурные паттерны

### Adopt

- Event-Driven Architecture - основа целевой слабосвязанной платформы, домены обмениваются событиями и реактивными потоками.
- Data Mesh - организационно-технический паттерн, домены владеют своими данными как продуктами.
- Domain-Driven Design, bounded contexts - основа нарезки доменов и контрактов между ними (см. Task4Advanced).
- Anticorruption Layer - изоляция от легаси (DWH, Camel) на период миграции с заранее определёнными критериями вывода.
- Self-service BI как принцип - бизнес-пользователь строит отчёты сам в пределах своего доступа, без очереди к центральной команде.

### Trial

- Data as a Product, дата-контракты - дата-продукт с владельцем, SLA, версионируемой схемой, тестами и документацией.
- CQRS для потоковых витрин - разделение модели записи в доменах и модели чтения в near-real-time витринах.
- Publisher / Subscriber между доменами - потребитель подписывается на существующий поток без изменений в источнике.
- Outbox для надёжной публикации событий - согласованность между изменением состояния и публикацией факта.
- FinOps как практика - управление облачными затратами через теги, бюджеты, unit-экономику дата-продуктов.

### Assess

- Kappa, streaming-first аналитика - единый потоковый путь обработки без отдельного пакетного контура, оценивается для части доменов.
- Data Fabric - метаданные и активный каталог как основа автоматизации доступа и интеграции, оценивается как дополнение к Data Mesh.
- Zero-copy обмен данными между доменами - доступ к данным без физического копирования (шеринг таблиц Iceberg), PoC.

### Hold

- Монолитный DWH с бизнес-логикой - централизация логики в общем хранилище тормозит time-to-market и связывает домены.
- Point-to-point синхронные интеграции на критическом пути - хрупкие связи, каскадные отказы, выводятся в этап 3.
- Ночной batch как единственный способ обмена - несовместим с целью перехода к near-real-time.

## Квадрант 2. Хранение, платформа, облако

### Adopt

- Object storage, S3-совместимое - базовый слой хранения сотен терабайт, разделение хранения и вычислений.
- Lakehouse на Apache Iceberg - табличный формат с ACID, эволюцией схемы и time travel поверх объектного хранилища.
- Managed Kubernetes - среда для сервисов платформы и доменных дата-продуктов.
- Terraform, IaC - вся инфраструктура и окружения доменов создаются кодом, переиспользуемыми модулями (см. Task1Advanced, Task2Advanced).
- Инфраструктура как переиспользуемые модули - домены получают типовое окружение self-service.

### Trial

- Trino - федеративные и интерактивные запросы к Lakehouse и внешним источникам.
- ClickHouse - хранилище под потоковые витрины и низколатентные агрегаты для портала.
- Data Catalog, OpenMetadata или DataHub - каталог, lineage, бизнес-глоссарий, реестр дата-продуктов.
- Feature Store для ИИ-сервисов - переиспользование признаков между обучением и inference.
- Iceberg REST-каталог, multi-engine - единый каталог таблиц для Trino, Spark, Flink.

### Assess

- Serverless-запросы, управляемый Trino или Spark - оплата за запрос вместо постоянного кластера, оценка по стоимости и латентности.
- Геораспределённое active-active хранилище - для критичных доменов при выходе в новые регионы.
- Управляемый Lakehouse одним вендором - оценивается как ускорение, но с риском vendor lock-in.

### Hold

- Microsoft SQL Server 2008 как DWH - вне поддержки вендора, не масштабируется под объёмы, узкое место аналитики.
- On-prem storage-массивы для аналитики - капитальные затраты и отсутствие эластичности.
- Собственный ЦОД под аналитическую нагрузку - не соответствует курсу на облако.

## Квадрант 3. Интеграция и обработка данных

### Adopt

- Apache Kafka как событийная шина - доменные топики, гарантированная доставка, порядок в пределах ключа агрегата.
- CDC через Debezium из SQL Server - вытаскивание изменений из легаси DWH в события без доработки самого DWH.
- Dead Letter Queue - изоляция необработанных сообщений, повторная обработка без потери данных.
- Schema Registry и контракты данных - версионирование схем событий, проверка совместимости в CI.
- dbt для пакетного ELT - регламентные преобразования и реконсиляция как версионируемый код с тестами.

### Trial

- Apache Flink - потоковая обработка, оконные агрегаты, обогащение событий для near-real-time витрин.
- Kafka Connect - типовые коннекторы источников и приёмников без собственного кода.
- Оркестрация, Airflow или Dagster - расписания и зависимости пакетных пайплайнов и обновления дата-продуктов.
- Data Quality, Great Expectations или Soda - проверки качества на входе и выходе дата-продуктов.
- Reverse ETL - возврат рассчитанных показателей из витрин в операционные системы.

### Assess

- Spark Structured Streaming - альтернатива Flink для команд с опытом Spark, оценка по стоимости и латентности.
- Flink SQL как основной инструмент витрин - декларативное описание потоковых витрин вместо кода.
- Materialize или RisingWave - инкрементально поддерживаемые материализованные представления на потоке.

### Hold

- Apache Camel ESB как основная интеграция - точечные маршруты, скрытая бизнес-логика в интеграционном слое, мост совместимости на период миграции.
- Хранимая бизнес-логика в процедурах DWH - переносится в домены-владельцы.
- Ручные выгрузки и сверки между системами - источник задержек и ошибок.

## Квадрант 4. BI, доступ, наблюдаемость

### Adopt

- Семантический слой метрик - единый источник определений показателей для всех отчётов и витрин.
- ABAC, RLS, маскирование PII - контроль доступа по атрибутам, строковая фильтрация, маскирование чувствительных полей.
- Data lineage и каталог данных - прослеживаемость происхождения данных, поиск и документация дата-продуктов.
- Observability, метрики, логи, трейсы - наблюдаемость пайплайнов, потоков и портала.
- CI/CD для данных и дата-продуктов - изменения схем, витрин и метрик проходят автотесты и деплой конвейером.

### Trial

- Портал self-service BI, SPA и конструктор отчётов - замена клиента PowerBuilder, построение отчётов по любым срезам в пределах доступа.
- Superset или Metabase как клиент - готовый инструмент визуализации поверх семантического слоя.
- SLA и SLO для дата-продуктов - свежесть, доступность, качество как измеримые обязательства домена.
- Каталог дата-продуктов с владельцами - витрина дата-продуктов с ответственным и условиями использования.
- Автотесты метрик в CI - защита от расхождения определений показателей между доменами.

### Assess

- Headless BI, слой метрик как API - потребление метрик внешними и встроенными приложениями через API.
- Embedded analytics для партнёров - встроенные отчёты для фарма-партнёров и производителя электроники.
- LLM-ассистент к семантическому слою - запрос отчётов на естественном языке поверх проверенных определений.

### Hold

- Клиент на PowerBuilder - устаревший стек, отсутствие развития, заменяется порталом.
- Power BI с кастомизациями поверх DWH - большое количество кастомной логики, завязанной на SQL Server 2008.
- Ручные Excel-сверки отчётности - не масштабируются, несовместимы с near-real-time.
