# Домены, bounded contexts и агрегаты

Разбиение системы "Будущее 2.0" по Domain-Driven Design. Для каждого bounded context указаны тип поддомена, назначение, ключевые агрегаты (корень, границы, инварианты, ключ) и роль в событийной интеграции.

## Классификация поддоменов

Core (конкурентное преимущество, разрабатывается своими силами):

- Пациентский поток
- ИИ-диагностика
- Кредитование
- Витрина данных и дата-продукты

Supporting (нужны бизнесу, но не уникальны):

- Идентификация клиента и MDM
- Медицинский биллинг
- Платежи и счета
- Управление персоналом
- Инвентаризация и оборудование
- Партнёрская интеграция
- Согласия и комплаенс-аудит
- Корпоративная финансовая консолидация

Generic (берётся готовое, кастомизация минимальна):

- Управление доступом (IAM)
- Уведомления

## Карта контекстов (context map)

Отношения между контекстами в терминах DDD:

- Идентификация клиента и MDM -> все контексты: Published Language (PL). MDM публикует единый `customerId` и словарь идентификаторов, остальные контексты - Conformist к этому языку.
- Пациентский поток -> ИИ-диагностика: Customer/Supplier. ИИ-диагностика - downstream, работает по событиям назначения исследования.
- Пациентский поток -> Медицинский биллинг: Publisher/Subscriber (событие завершения визита).
- ИИ-диагностика -> Медицинский биллинг: Publisher/Subscriber (событие прохождения исследования как основание для начисления).
- Медицинский биллинг -> Кредитование: Publisher/Subscriber (выставленный счёт как триггер предложения рассрочки).
- Медицинский биллинг -> Платежи и счета: Customer/Supplier.
- Кредитование -> Платежи и счета: Customer/Supplier (график платежей и списания по договору).
- Партнёрская интеграция -> Инвентаризация и оборудование, ИИ-диагностика: Open Host Service + Anticorruption Layer. Внешние API фарма-партнёров и производителя электроники нормализуются в доменные события.
- Легаси DWH (SQL Server 2008) и шина Camel -> платформа: Anticorruption Layer. CDC из DWH и адаптеры Camel превращают легаси-данные в события; слои временные, с критериями вывода.
- Все контексты -> Витрина данных и дата-продукты: Publisher/Subscriber. Витрина - downstream Conformist, на приёме стоит ACL. Медицинские карты, истории болезни и результаты исследований в витрину не публикуются.
- Все контексты -> Согласия и комплаенс-аудит: Publisher/Subscriber.
- Все контексты -> Корпоративная финансовая консолидация: Publisher/Subscriber.
- Все контексты -> Уведомления: Publisher/Subscriber.

## Bounded contexts и агрегаты

### Пациентский поток (core)

Регистрация пациентов, запись на приём, ведение визитов и назначений. Медицинский контент (карты, истории болезни) остаётся внутри контекста и наружу как аналитические данные не отдаётся.

Агрегат "Пациент"

- Корень: Пациент.
- Границы: демографические данные, ссылка на `customerId` из MDM, список согласий на обработку, контактные данные. Медкарта - отдельный агрегат внутри контекста, наружу не публикуется.
- Инварианты: у пациента ровно один активный мастер-идентификатор клиента; регистрация невозможна без хотя бы одного подтверждённого согласия на обработку персональных данных.
- Ключ: `patientId` (UUID), плюс внешний `customerId`.

Агрегат "Запись на приём"

- Корень: Запись на приём.
- Границы: пациент, врач, услуга, слот времени, статус (создана, подтверждена, отменена, проведена).
- Инварианты: слот врача не может быть занят двумя подтверждёнными записями; отмена возможна только до наступления слота; переход в статус "проведена" только из "подтверждена".
- Ключ: `appointmentId` (UUID).

Агрегат "Визит"

- Корень: Визит (эпизод обслуживания).
- Границы: пациент, врач, дата, перечень оказанных услуг, назначения (в том числе на ИИ-исследование), итоговый статус.
- Инварианты: визит закрывается только с непустым перечнем услуг; после закрытия состав услуг неизменяем; каждое назначение ссылается на существующую услугу.
- Ключ: `encounterId` (UUID).

### ИИ-диагностика (core)

Проведение исследований медицинских данных с помощью ИИ-моделей, формирование заключений для врача.

Агрегат "Исследование ИИ"

- Корень: Исследование ИИ.
- Границы: ссылка на назначение и визит, тип исследования, версия модели, входной набор данных (по ссылке), статус (создано, в очереди, выполняется, пройдено, ошибка), метрики качества прогона.
- Инварианты: исследование привязано ровно к одному назначению; статус "пройдено" достижим только после успешного прогона модели; версия модели фиксируется в момент запуска и далее не меняется.
- Ключ: `studyId` (UUID).

Агрегат "Заключение ИИ"

- Корень: Заключение ИИ.
- Границы: ссылка на исследование, структурированные выводы, уровень уверенности, признак необходимости подтверждения врачом.
- Инварианты: заключение существует только для исследования в статусе "пройдено"; ровно одно действующее заключение на исследование; при уровне уверенности ниже порога флаг подтверждения врачом обязателен.
- Ключ: `reportId` (UUID).

### Медицинский биллинг (supporting)

Начисление за оказанные медицинские услуги и ИИ-исследования, выставление счетов клиенту.

Агрегат "Счёт за медицинские услуги"

- Корень: Счёт.
- Границы: клиент, ссылка на визит, позиции счёта (услуга, количество, цена), валюта, итоговая сумма, статус (черновик, выставлен, частично оплачен, оплачен, аннулирован).
- Инварианты: итоговая сумма равна сумме позиций; выставленный счёт неизменяем, корректировка - только сторно-счётом; сумма оплат не превышает итог счёта; аннулирование возможно только из статуса "выставлен" без платежей.
- Ключ: `invoiceId` (UUID); номер счёта уникален в пределах юридического лица.

### Кредитование (core)

Скоринг, оформление и сопровождение кредитных договоров и рассрочек, в том числе на оплату лечения.

Агрегат "Кредитная заявка"

- Корень: Кредитная заявка.
- Границы: клиент, запрошенная сумма и срок, цель (в том числе ссылка на счёт за лечение), результат скоринга, статус (подана, на рассмотрении, одобрена, отклонена, аннулирована).
- Инварианты: сумма и срок в пределах продуктовых лимитов; переход в "одобрена" только при положительном скоринге; из одной заявки создаётся не более одного договора.
- Ключ: `loanApplicationId` (UUID).

Агрегат "Кредитный договор"

- Корень: Кредитный договор.
- Границы: клиент, ссылка на заявку, сумма, ставка, срок, график платежей, остаток задолженности, статус (создан, действует, просрочен, погашен, расторгнут).
- Инварианты: сумма договора равна одобренной по заявке; график платежей покрывает всю сумму с процентами; остаток задолженности не отрицателен; статус "погашен" - только при нулевом остатке.
- Ключ: `creditContractId` (UUID); номер договора уникален в пределах банка.

### Платежи и счета (supporting)

Ведение расчётных счетов клиента, проведение платежей и списаний, обработка платежей по кредитам.

Агрегат "Счёт клиента"

- Корень: Счёт клиента.
- Границы: клиент, номер счёта, валюта, баланс, статус (открыт, заблокирован, закрыт), лимиты.
- Инварианты: баланс не уходит ниже разрешённого лимита; операции по закрытому или заблокированному счёту запрещены; валюта счёта неизменяема.
- Ключ: `accountId` (UUID); номер счёта уникален.

Агрегат "Платёж"

- Корень: Платёж.
- Границы: счёт-источник, назначение (счёт за услуги или платёж по кредиту), сумма, валюта, статус (создан, проведён, отклонён, возвращён), идемпотентный ключ операции.
- Инварианты: сумма положительна; проведение уменьшает баланс счёта-источника ровно один раз; повторная обработка того же идемпотентного ключа не создаёт новый платёж; возврат не превышает сумму платежа.
- Ключ: `paymentId` (UUID); `operationKey` уникален.

### Идентификация клиента и MDM (supporting)

Единый мастер-профиль клиента и связывание идентификаторов из клиник, банка, партнёров.

Агрегат "Мастер-профиль клиента"

- Корень: Мастер-профиль клиента.
- Границы: `customerId`, набор связанных внешних идентификаторов (клиника, банк, партнёр), статус слияния, атрибуты уровня party (тип, наименование, статус).
- Инварианты: один внешний идентификатор принадлежит не более чем одному мастер-профилю; слияние двух профилей необратимо и сохраняет историю; активный мастер-профиль ровно один на клиента.
- Ключ: `customerId` (UUID).

### Управление персоналом (supporting)

Кадровый учёт сотрудников клиник и офиса, назначения и ставки.

Агрегат "Сотрудник"

- Корень: Сотрудник.
- Границы: персональные данные, подразделение, должность, назначения (период, ставка, роль), статус (принят, в отпуске, уволен).
- Инварианты: у сотрудника не более одного активного основного назначения; период назначения не пересекается с другим основным назначением; после увольнения новые назначения запрещены.
- Ключ: `employeeId` (UUID); табельный номер уникален.

### Инвентаризация и оборудование (supporting)

Учёт медицинского оборудования и расходных запасов, поставки, пороги пополнения.

Агрегат "Позиция запаса"

- Корень: Позиция запаса.
- Границы: номенклатура, склад, текущее количество, минимальный порог, единица измерения.
- Инварианты: количество не отрицательно; при количестве ниже порога позиция помечается как требующая пополнения; списание не превышает остаток.
- Ключ: `stockItemId` (UUID).

Агрегат "Единица оборудования"

- Корень: Единица оборудования.
- Границы: тип, серийный номер, привязка к клинике и кабинету, статус (в эксплуатации, на обслуживании, выведено), даты поверки.
- Инварианты: серийный номер уникален; эксплуатация запрещена при просроченной поверке; вывод из эксплуатации необратим для этой единицы.
- Ключ: `equipmentUnitId` (UUID); серийный номер уникален.

### Партнёрская интеграция (supporting)

Приём данных от фарма-партнёров и производителя медицинской электроники, публикация во внутренние события через ACL.

Агрегат "Партнёрская поставка"

- Корень: Партнёрская поставка.
- Границы: партнёр, перечень позиций (препарат или оборудование, количество, партия, срок годности), статус (зарегистрирована, принята, отклонена), ссылки на исходные сообщения партнёра.
- Инварианты: поставка принадлежит одному партнёру; позиции с истёкшим сроком годности не принимаются; принятая поставка неизменяема.
- Ключ: `partnerShipmentId` (UUID); пара "партнёр + номер поставки партнёра" уникальна.

Агрегат "Позиция каталога препаратов"

- Корень: Позиция каталога.
- Границы: код препарата, наименование, форма выпуска, партнёр-источник, версия записи.
- Инварианты: код препарата уникален в пределах партнёра; действующая версия записи ровно одна; изменения создают новую версию.
- Ключ: `drugCatalogItemId` (UUID).

### Согласия и комплаенс-аудит (supporting)

Управление согласиями клиента на обработку данных и неизменяемый аудит доступа к чувствительным данным.

Агрегат "Согласие"

- Корень: Согласие.
- Границы: клиент, цель обработки, области данных, срок действия, статус (действует, отозвано, истекло), история изменений.
- Инварианты: пересекающихся действующих согласий на одну цель не более одного; отзыв необратим для этой версии согласия; истечение срока автоматически переводит в статус "истекло".
- Ключ: `consentId` (UUID).

Агрегат "Аудиторская запись"

- Корень: Аудиторская запись.
- Границы: субъект доступа, ресурс, действие, решение политики, время, контекст запроса.
- Инварианты: запись неизменяема после создания (append-only); каждая запись ссылается на конкретное решение политики доступа.
- Ключ: `auditRecordId` (UUID).

### Корпоративная финансовая консолидация (supporting)

Сведение финансовых показателей направлений в единую отчётность головного офиса.

Агрегат "Консолидационный период"

- Корень: Консолидационный период.
- Границы: период, набор направлений, статусы сборки по направлениям, итоговые агрегаты, признак закрытия.
- Инварианты: закрытый период неизменяем; консолидация выполняется только при получении данных по всем обязательным направлениям; повторное закрытие запрещено.
- Ключ: `consolidationPeriodId` (год и месяц).

### Витрина данных и дата-продукты (core)

Портал самообслуживания и доменные дата-продукты. Контекст только читает события, на домены не влияет.

Агрегат "Определение отчёта"

- Корень: Определение отчёта.
- Границы: владелец, набор метрик и измерений, фильтры, уровень доступа, расписание обновления.
- Инварианты: все метрики отчёта существуют в семантическом слое; уровень доступа отчёта не ниже уровня самой чувствительной используемой метрики; в отчёт нельзя включить запрещённые к аналитике медицинские данные.
- Ключ: `reportDefinitionId` (UUID).

Агрегат "Дата-продукт"

- Корень: Дата-продукт.
- Границы: домен-владелец, контракт (схема, SLA, гарантии свежести), список источников-событий, версия.
- Инварианты: у дата-продукта ровно один домен-владелец; публикация новой версии не ломает действующий контракт (обратная совместимость) либо выпускается новый major; каждый источник-событие зарегистрирован в реестре схем.
- Ключ: `dataProductId` (UUID).

Агрегат "Подписка на отчёт"

- Корень: Подписка.
- Границы: отчёт, получатель, канал доставки, расписание, уровень доступа получателя.
- Инварианты: уровень доступа получателя не ниже уровня доступа отчёта; неактивная подписка не порождает доставок.
- Ключ: `subscriptionId` (UUID).
